# tdd — test-driven development через red-green loop

Test-driven development — это не «тесты потом», а дисциплина, в которой код
рождается из failing теста. Каждая цикл учит агента одной вещи о задаче:
тест описывает наблюдаемое поведение, минимальная имплементация делает его
зелёным, и так шаг за шагом. Цикл **не предвидит** будущие тесты и не строит
фреймворк заранее — он реагирует только на то, что требует текущий тест.

Тон этого скила: **тестируй поведение через public интерфейс, не internal
детали**. Тесты — это контракт с внешним миром, не спецификация приватных
механизмов. Если тест ломается при рефакторинге внутренностей — это
implementation-coupled тест, его не должно было быть.

## Когда применять

- Пишешь новую фичу или существенный фикс бага — веди test-first.
- Пользователь явно просит TDD / red-green.
- У точки кода есть чёткий наблюдаемый контракт (функция, эндпоинт, команда,
  обработчик события), который можно выразить как assertion.
- НЕ применяй слепо для throwaway-экспериментов, research-spike'ов или
  прототипов, цель которых — узнать, возможна ли вообще идея; там цикл ниже.

## Правила

1. **Red-green loop, не «тесты потом».** Сначала напиши failing тест, увидь
   его падение по правильной причине (assertion не проходит, а не ImportError),
   затем напиши минимальный код, делающий именно этот тест зелёным.
2. **Одна цикл = одна seam = одна test = одна minimal implementation.** Не
   пихай два поведения в одну cycle. Не добавляй assertion, не относящийся к
   текущему seam'у — заведи следующий cycle.
3. **Минимально, не предвидя.** Имплементация делает *текущий* тест зелёным и
   ничего более. Никаких «заодно добавлю параметр на будущее», «обобщу под
   случаи», «вынесу helper, чтобы потом переиспользовать». Будущее раскроют
   следующие тесты — доверься им.
4. **Тестируй через public interface.** Seams живут на границах модуля:
   public API, CLI-команда, HTTP-эндпоинт, событие. Не тестируй приватные
   методы, не мокай internal collaborators ради наблюдения их вызовов.
5. **Идеальное число seams = 1, приоритет existing seams.** Каждый новый seam
   — это новая surface area, которую нужно поддерживать. Прежде чем заводить
   новый seam (новый публичный метод, новый hook), проверь, нельзя ли выразить
   поведение через уже существующий.
6. **Fixed seams — согласовывай с пользователем.** Если seam приходится
   зафиксировать (договориться о форме API до реализации), это решение уровня
   контракта — подтверди его с человеком, не фиксируй молча.
7. **Vertical slices, не horizontal.** Один test → implementation → repeat.
   Каждый test — tracer-bullet: отзывчив на то, чему научила предыдущая
   cycle, а не на абстрактной декомпозиции. Запрещён паттерн «все тесты
   пачкой, потом вся имплементация»: он убивает обратную связь цикла.
8. **Рефакторинг — отдельная фаза review, не часть loop.** Внутри cycle ты
   либо red→green, либо (после зелёного) refactor — но refactor дублирует
   поведение, не меняет его, и подчиняется правилу «все существующие тесты
   остаются зелёными». Не маскируй рефакторинг под новую cycle.
9. **Реальная минимальность, не спектакль.** «Минимальная имплементация» — не
   тупой return constant, который пройдёт assertion случайно; это наименьший
   правдивый код, реализующий наблюдаемое поведение. Constant return
   допустим только если он корректен для всех будущих тестов этого seam'а.

## Цикл / Шаги

Один проход red-green:

1. **Red — опиши поведение тестом.** Напиши тест через public интерфейс,
   выражающий одно наблюдаемое поведение. Запусти — падает, и по *ожидаемой*
   причине (отсутствует поведение), а не по синтаксису/импорту.
2. **Green — минимально сделай зелёным.** Напиши наименьший правдивый код,
   проходящий текущий тест. Не заглядывай вперёд. Запусти — зелёный.
3. **Conscience-check — одна cycle одна lesson.** Перед переходом: добавил ли
   я только то, что требует текущий тест? Если вылезло лишнее — отрежь.
4. **Повтори** для следующего поведения того же seam'а или нового seam'а
   (по приоритету existing seams). Каждая новая cycle опирается на урок
   предыдущей: тесты используются как probe, а не как план из N случаев,
   написанных заранее.

Фаза **review** (опционально, после серии cycles):

5. **Refactor.** При зелёном состоянии тестов — упрощай, убирай дубликаты,
   переименовывай. Тесты остаются зелёными на каждом шаге. Если тест упал
   при рефакторинге — это либо баг рефакторинга, либо implementation-coupled
   тест: разберись, не откатывай молча.

## Анти-паттерны

- **Implementation-coupled тест.** Мокает internal collaborators, проверяет
  приватные методы, лезет в side-channel (spied calls, внутреннее состояние).
  Симптом: тест ломается при рефакторинге, хотя наблюдаемое поведение
  сохранено. Каждое появление — повод передвинуть seam на public интерфейс.
- **Tautological тест.** Assertion пересчитывает ожидаемое значение тем же
  способом, каким его считает проверяемый код (`assert f(x) == same_formula(x)`).
  Тест проходит всегда, баг не ловит. Expected должен быть записан как
  литерал / независимая константа, не повторять логику SUT.
- **Horizontal slicing.** Пачка тестов -> пачка имплементации. Убивает
  tracer-bullet обратную связь: ты не учишься у каждого теста, а угадываешь
  заранее — то самое «предвидение», которое loop запрещает.
- **Спектакль-минимальность.** `return 42` проходит один assertion, но
  заведомо сломается на следующем тесте того же seam'а — это не минимальность,
  а отложенный два раза red. Минимальность правдива, не нарочито тупа.
- **Refactor внутри цикла.** «Допишу имплементацию и заодно уберу
  дубликаты» в одной cycle растворяет границу green/refactor и прячет
  изменение поведения под мнимой чисткой. Сначала green, потом — отдельная
  фаза review.
- **Молчаливый новый seam.** Завёл новый public метод/hook, не согласовав —
  зафиксировал контракт без человека. Fixed seams → к пользователю.

## Результат / критерий готовности

- Каждая имплементационная единица рождена из failing теста; ни одной строки
  production-кода, не оправданной текущим тестом.
- Все тесты зелёные; refactoring-фаза (если была) не сломала их.
- Каждый тест обращается к public интерфейсу — приватные методы и внутренние
  моки отсутствуют.
- Тесты не пересчитывают expected той же формулой, что SUT (нет тавтологии).
- Slice'и вертикальны: каждая cycle отзывчива уроку предыдущей, а не
  заранее написанному плану из всех случаев сразу.

## Что дальше

- Доведённая до зелёного фича — переход к `improve` (review/доработка) или к
  следующему тикету из плана.
- Если в цикле обнаружен новый seam, требующий фиксации — согласуй через
  `grilling`/профиль, не вскрывай молча.
