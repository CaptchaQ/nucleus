# ux-review — UX-ревью с frequency-gate

Скил проверяет UI-изменения по двум гейтам: **сначала «вообще ли делать»
(frequency-gate), потом «как сделать» (эвристики + escalation-триггеры)**.
Ревью не угадывает feel и perceived perf из кода — оно выставляет feel-checks в
план. Успех ревью — ноль лишних строк: «actually delete is the measure».

## Когда применять

- Перед любым UI-изменением, которое уходит в прод (новый компонент, правка
  существующего экрана, animation, spacing/цвет, ввод нового токена).
- Когда в PR есть `transition`, `animation`, `transform: scale`, `duration`,
  кастомный easing, изменение spacing-сетки или visible affordance.
- Перед ручной отрисовкой новой визуальной сцены — чтобы не пилить её по чужим рефлексам.

## Правила

1. **Frequency-gate — первый гейт.** Прежде «как сделать» спроси «вообще ли
   делать». Ответ из таблицы частот ниже, не из вкуса.
2. **No invented values.** Численные значения (`duration`, `easing`, spacing
   scale, breakpoints, radius) тяни из каталога/таблицы (см. ниже) или из
   дизайн-системы/профиля проекта. Не выдумывай. Нет значения → спроси человека,
   не подставляй похожее.
3. **Strict output.** Ревью выдаёт таблицу `Before | After | Why` (таблицей,
   списком — запрещено) + вердикт `Block`/`Approve` по критериям. Любое
   несоответствие правилу — отдельная строка таблицы.
4. **Default to flagging.** Одобрение заработывается, не даётся по умолчанию.
   Молчание в условиях задачи = Block с пометкой «не доказано, что нужно».
5. **Escalation-триггеры флагают сразу**, без дискуссии (см. список). Их нет в
   таблице эвристик — это auto-raise, отдельный раздел вердикта.
6. **«Actually delete is the measure».** Нулевые строки кода — успех.
   Remedial hierarchy ставит «удалить» на 1 место, «упростить» на 2, «сделать
   иначе» на 3. Если можно удалить — не предлагай заменить.
7. **Honest tone.** Feel, perceived perf, accessibility-ощущения нельзя проверить
   из кода → ставь feel-check в план (медленный просмотр, реальное устройство,
   свежие глаза, `prefers-reduced-motion`). Не угадывай и не вписывай «looks good».

## Каталог значений (no invented values)

Если значение есть в профиль/дизайн-системе проекта — берёшь оттуда, не отсюда.
Каталог ниже — fallback, когда профиль молчит. Не комбинируй свои значения.

### Таблица частот (frequency-gate)

| Частота действия | Вердикт по усложнению/UI-polish | Действие |
|---|---|---|
| 100+/день (high-frequency: tap row, open menu, send, scroll) | **Никогда** не анимируй, не добавляй affordance, не новый motion-слой | Оставить как есть или удалить лишнее |
| Десятки/день (mid: open modal, switch tab, confirm) | Почти невидимо: 100–150ms, standard ease | Минимальный feedback, без delight |
| 1–несколько/день (low: onboarding, first-run, success state) | Можно delight, но measured | Допускается motion/праздничность |
| Редко/разово (empty state, error, milestone) | Полный delight допустим | Свобода, но в рамках дизайн-системы |

Стартуй с этой таблицы. Если действие high-frequency и в PR есть `transition` —
это Block до оправдания.

### Каталог durations (fallback, если профиль молчит)

| Назначение | duration | ease |
|---|---|---|
| High-frequency feedback (tap, hover state) | 100–120ms | `ease-out` |
| Стандартный transition (toggle, open panel) | 150–200ms | `ease` / `cubic-bezier(.2,0,0,1)` |
| Large enter/exit (modal, sheet) | 200–250ms | `cubic-bezier(.2,0,0,1)` |
| Delight (low-freq celebration) | 250–300ms | кастомный (из дизайн-системы) |
| **> 300ms** | **Block** (escalation) — исключение только с обоснованием | — |

### Каталог easings

`ease`, `ease-out`, `ease-in-out`, `cubic-bezier(.2,0,0,1)` (standard decel),
`cubic-bezier(.4,0,.2,1)` (material standard). Любой другой easing —
изобретённый, → escalation.

### Spacing scale (fallback)

`0, 2, 4, 8, 12, 16, 24, 32, 48, 64` (px, base 8, допуски 2/4 для текста). Values
вне шкалы → escalation, спрашивай дизайн-систему. Radius — из того же масштаба;
не комбинируй свои радиусы.

### Breakpoints (fallback)

`640, 768, 1024, 1280` (px). Свой брейкпоинт — escalation.

## Escalation-триггеры (flag сразу)

При встрече в PR — Block без обсуждения, в отдельном разделе вердикта.

1. `transition: all` — анимирует всё, ломает перф и намерение.
2. `transform: scale(0)` / `scale(0.99-эффект)` как «появление» — изобретённый
   паттерн, обычно скрывает отсутствие proper enter animation.
3. `duration > 300ms` без обоснования и без low-frequency gate.
4. Изобретённый `cubic-bezier`/`ease-*` вне каталога или дизайн-системы.
5. Spacing/radius/breakpoint вне шкалы.
6. Нерелевантная анимация high-frequency действия (motion там, где достаточно
   мгновенной смены состояния).
7. Visual affordance добавлен без проверки нового use-case.
8. `prefers-reduced-motion` не учтён там, где есть `transition`/`animation`.
9. Контраст/`aria`/`focus` отсутствует на визуально главном действии.
10. Hardcoded hex там, где есть token/палитра проекта.

## UX-эвристики (keepsimple.io uxcore — универсальные)

Проходишь по чек-листу; каждое несоответствие → строка в таблицу Before/After/Why.

| Эвристика | Что проверяешь |
|---|---|
| Ясность главного действия | На экране есть одно ясно главное действие? Нет конкурирующих CTA одной визуальной силы? |
| Иерархия | Порядок чтения следует размеру/весу? Главное — крупнее, второстепенное — тише? |
| Обратная связь на действие | Каждое действие пользователя даёт мгновенный видимый отклик (для high-freq — мгновенно, без motion)? |
| Консистентность | Тот же паттерн товара/действия в проекте использует те же spacing, типографику, радиус, motion-token? |
| Доступность | Контраст ≥ целевого, видимый `:focus`, `aria-*` на некратком контенте, keyboard path работает без мыши? |
| Нагрузка на когницию | Сколько решений пользователь принимает одновременно? Можно ли убрать шаг / подать значение по умолчанию? |
| Frequency match | UI-polish соответствует частоте действия из frequency-gate? |

## Цикл

1. **Запиши что ревьюишь.** Компонент/экран/правка одной строкой + основное
   действие пользователя на нём.
2. **Frequency-gate.** Какое действие тут происходит чаще всего, по таблице
   частот? Нужно ли вообще усложнять/добавлять motion/affordance? Если
   high-frequency и есть усложнение — это Block до оправдания.
3. **Пройди эвристики + escalation.** Чек-эвристики выше → каждая находка
   становится строкой `Before | After | Why`. Escalation-триггеры → отдельный
   раздел блока в вердикте.
4. **Verdict + feel-checks.** `Block`/`Approve` + критерий. Везде, где не можешь
   проверить из кода (feel, perceived perf, reduced-motion на устройстве, свежие
   глаза) — записывай feel-check в план с конкретным способом проверки. Не
   считай готовым, пока feel-check не проведён.

## Результат / критерий готовности

Вывод содержит:

1. **Что ревьюили** (компонент/экран + основное действие, 1 строка).
2. **Frequency-gate-вердикт** (какая частота, нужно ли усложнение).
3. **Таблица `Before | After | Why`** (по эвристикам; минимум — строки для каждой
   находки, пустых допусков не неси).
4. **Escalation-блок** (перечень сработавших триггеров или «нет»).
5. **Вердикт `Block`/`Approve`** + 1–2 критерия.
6. **Feel-checks** — список конкретных проверок, которые нельзя сделать из кода:
   медленный просмотр, реальное устройство, `prefers-reduced-motion`, свежие
   глаза. Каждый — с указанием как её выполнить и кто проверяет.

Одобрение выдаётся только если: frequency-gate пройден, escalation-триггеры
отсутствуют или обоснованы (low-frequency), эвристики без замечаний или
исправлены в той же правке, feel-checks запланированы. Иначе — Block с пометкой
что именно мешает и remedial hierarchy (1. удалить, 2. упростить, 3. сделать
иначе).
