# prototype — один дизай-вопрос, runnable ответ

Прототип — **throwaway программа, которая отвечает на один дизай-вопрос**.
Не «построить приложение», а выяснить одно: *как этот кусок должен
выглядеть/вести* (UI-ветвь) *или* *правильно ли state-модель* (logic-ветвь).
Вопрос решает форму артефакта — выбор ветви ошибся, прототип впустую.

**Throwaway — это ограничение на КАК писать**, не обещание уничтожить: нет
error handling, нет тестов, нет production-polish, нет абстракций — ровно
столько, чтобы прототип *запустился и ответил*. Но *ответ* survives: сворачивается
в реальный код/спеку, а сам прототип остаётся **primary source** — ссылайся на
него из impl-задачи (коммит на ветке `prototype/<name>` или в
`.agent-forge/prototypes/<name>/`). Main хранит только валидированное решение;
прототип живёт отдельно, чтобы его можно было пере-открыть.

## Когда применять

- Дизай-вопрос нельзя решить на бумаге/в голове — нужно *почувствовать*:
  как поведение UI, как state-машина проходит сквозь edge-cases.
- Вопрос звучит как «должно ли это быть A или B?», «как это выглядит?»,
  «прошивается ли эта state-модель, если нажать туда-то трижды?».
- НЕ путай с `implement`: implement строит production по спеке/ticket —
  это billing-фаза. prototype *генерирует* спеку/insight, отвечая на вопрос.
  Если ответ уже зафиксирован в плане/ADR — это `implement`, не `prototype`.

## Правила

1. **Один дизай-вопрос на прототип.** Утверди его одним предложением *до*
   написания кода (что выясняем, что значит «ответ получен»). Два вопроса =
   два прототипа. «Построить дашборд» — не вопрос; «куда клать notification
  badge — на иконку или рядом?» — вопрос.
2. **Дивергентность для UI — обязательно.** UI-прототип строит **N разных
   вариантов** (по умолчанию 3, до 5), чтобы *сравнить*, а не один угаданный
   «лучший». Каждый вариант расходится на **именованной оси** (layout / density
   / personality / motion / interaction-model) — ось формулируется фразой до
   кода. Варианты, отличающиеся только цветом/копирайтом, — это *один* вариант;
   замени на реальную альтернативу. Имена описывают направление («Quiet»,
   «Dense», «Playful»), не «Option A/B/C».
3. **Спецификация инструмента/picker — verbatim, не дизайн-решение агента.**
   Хардкод-инфраструктура (picker, harness, состояние для flip-сравнения)
   одинакова во всех проектах — копируй её как spec, не «дизайни» заново. Это
   chrome, не конкурсант: не подстраивай под токены/шрифты/бренд проекта.
   Решение тратится на *варианты*, не на обвязку.
4. **Low fidelity осознанно.** Outline, rough take, stub, произвольные но
   правдоподобные данные (реальные по форме имена/числа — не lorem ipsum, не
   мёртвые кнопки). Нет тестов, нет error handling кроме нужного для runnable,
  нет production-абстракций. Разрешён код-дугадка — его не пошлют в prod.
5. **Each variant fully works.** Реальные взаимодействия, реальная логика,
   full-size в реалистичном окружении (toast — поверх страницы, card — со
   соседями, кнопка — в форме). Side-by-side thumbnails и postage-stamp размер
   искажают spacing/scale — никогда не суди UI так. Flip — действие 100+/сесс,
   частотное правило: **сменa варианта мгновенная**, без анимации.
6. **Не трогай production во время exploration.** Всё живёт в изолированной
   prototype-поверхности (`/prototypes/<slug>`, отдельный route, или
   standalone HTML-файл). Ничего из неё не импортится в prod. Интеграция —
   только на шаге сворачивания, только для выбранного варианта.
7. **Capture после ответа.** Сверни валидированное решение в реальный
   код/спеку; прототип оставь как **primary source** на ветке
   `prototype/<name>` или в `.agent-forge/prototypes/<name>/`, и оставь
   context-pointer (ссылку) на impl-задаче. Зафиксируй *вердикт* и *вопрос,
   который он закрыл* — в задаче/коммите. Main хранит только решение.

## Цикл / Шаги

1. **Сформулируй один дизай-вопрос.** Одно предложение: что выясняем, что
   закроет вопрос. Если у промпта два вопроса — выбери высший-leverage один,
   остальные предложи как follow-up. Сформулируй * What would "answer received" look like*.
2. **Выбери ветвь** по сути вопроса (или по окружающему коду, если вопрос
   двусмыслен и человек недоступен — тогда заяви assumption в шапке прототипа):
   - **UI-ветвь** — «как должно выглядеть/вести?» → несколько расходящихся
     вариантов на одной поверхности, переключаемых (URL search-param + плавающий bottom-bar, или keyed re-mount).
   - **Logic-ветвь** — «правильно ли state-модель?» → единый shareable артефакт,
     который прогоняет state-машину сквозь случаи, которые трудно удержать в
     голове: free-play кнопки + tabbed guided walkthroughs, вывод полного
      relevant state после каждого действия.
3. **Выбери fidelity** — минимально достаточный под вопрос:
   `outline` (скелет/схема, если вопрос про структуру) → `stub` (фейковые данные,
     если вопрос про взаимодействие) → `code` (рабочая логика/motion, если
     вопрос про feel/dynamics). Решение тратится на вариативность *внутри*
     выбранного fidelity, не на рост fidelity.
4. **Recon再说** *(до дизайна)* — map точку опоры: stack/framework, styling-system,
   tokens (colors/radii/easing/duration), personality продукта, контекст рендера.
   Варианты используют *эти* токены — каждый должен выглядеть как мог бы
   выйти в этом продукте завтра. Проекта нет → standalone HTML, restrained
   defaults (нейтральные grays, один акцент, system font).
5. *(Только UI)* **Построй набор вариантов.** По умолчанию 3; до 5 если дизайн-пространство
   реально широкое и человек просит; **>5 dilutes сравнение**. До кода — лист
   \[name + axis\] на каждый; критерий готовности: ни у двух вариантов нет
   совпадающей оси. Построй **picker-harness** по верbatim-спеке; harness рендерит
   один вариант full-size за раз, мгновенная смена. Запусти, сам перекликая все
   варианты — console чист, взаимодействия отвечают.
6. **Сравни сам, потом представ.** Flip-ни все варианты; если два сошлись —
   отрежь один и скажи (picker с двумя настоящими направлениями лучше, чем три
   раздутых). Представь таблицей и **стоп — выбор принадлежит человеку**:

   | # | Variant | Axis | Когда это правильно | Его цена |
   | --- | --- | --- | --- | --- |
7. **Решение/insight → сворачивание.** Когда человек выбрал (UI) или прототип
   ответил (logic): интегрируй выбранное туда, где ему место, по конвенциям
   проекта (file layout, naming, tokens). Затем оставь прототип как **primary
   source** (`prototype/<name>` ветка или `.agent-forge/prototypes/<name>/`),
   оставь pointer (ссылку) из impl-задачи, и зафиксируй вердикт + закрытый
   вопрос в задаче/коммите. Если нужен ещё раунд — охрани harness и расходись
   *вокруг* направления, к которому подтянулся человек.

## Результат / критерий готовности

- Один дизай-вопрос сформулирован явно; ветвь (UI/logic) и fidelity выбраны и
  заявлены.
- UI: ≥3 по-настоящему расходящихся варианта с именами и осью, ни одна пара не
  делит ось; каждый full-size, в реалистичном окружении, со работающими
  взаимодействиями и правдоподобными данными. Picker сверстан по spec, flip
  мгновенный; console чист.
- Logic: единый runnable артефакт (HTML/standalone), прогоняющий state-машину
  сквозь named edge-cases, вывод полного relevant state после каждого действия.
- Прототип не трогает prod (изолированная поверхность; ничего не импортится в main).
- **Ответ заснят**: вердикт + закрытый вопрос — в impl-задаче/коммите; прототип
  живёт как primary source по указателю (`prototype/<name>` ветка или
  `.agent-forge/prototypes/<name>/`); pointer из impl-задачи на него стоит.
- Main хранит только валидированное решение; человек видел таблицу вариантов
  (UI) и задержал выбор за собой.

## Что дальше

- Выбранный вариант / подтверждённая state-модель → `implement` (или `to-spec`
  → `to-tickets`, если ответ превращается в несколько задач).
- Ещё туманно вокруг обоснованного направления → следущий раунд prototype
  (`prototype <slug> ×5` / divergence вокруг выбранной оси).
