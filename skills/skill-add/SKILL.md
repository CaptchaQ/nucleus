# skill-add — добавление нового скила

Набор живёт в `skills/<name>/SKILL.md` (ядро) и `skills/library/<name>/SKILL.md`
(библиотека, подгружаемая под проект через `stitch`). Когда повторяемая
процедура возникает второй раз — оформи её как скил.

## Когда применять

- Одна и та же последовательность действий встретилась второй раз.
- Человек: «запомни, как мы это делаем», «сделай скил», «кодифицируй методику».
- Известная методика (TDD, code review, deploy, ux-review) должна стать частью
  набора.
- `stitch` не нашёл нужного скила в библиотеке → сначала `skill-add`, потом
  `stitch` подгрузит.

## НЕ применять

- Единичная задача — это не скил, просто выполни её.
- Если процедура уже описана в другом скиле — **дополни тот**, не плоди.

## Ядро или библиотека?

- **Ядро** (`skills/<name>/`) — скилы, активные всегда в любом проекте:
  grilling, spec, wayfinder, orchestrate, improve, review, stitch, skill-add,
  domain, setup. Редко добавляется.
- **Библиотека** (`skills/library/<name>/`) — проектные скилы, подгружаемые под
  домен/стек: tdd, debug, ux-review, api-design, prototype. Сюда — большинство
  новых.

## Шаблон SKILL.md

```markdown
---
name: <kebab-case-имя>
description: <одно предложение: что делает и когда применять. Без слова "skill">
when: <condition для runtime-активации харнессом — конкретная ситуация>
---

# <имя> — <короткое название>

<1–2 абзаца: что это, в какой фазе применяется>

## Когда применять
- <условие 1>
- <условие 2>

## Правила
1. <правило — обязательное, иначе скил бесполезен>
2. <правило>

## Цикл / Шаги
1. <шаг с ожидаемым результатом>
2. <шаг>

## Результат / критерий готовности
<что должно существовать после применения скила>

## Что дальше
<какой скил обычно следующий>
```

## Правила добавления

1. **Имя** — kebab-case, короткое, без «skill-» префикса и без названия
   проекта. `code-review`, `tdd`, `deploy` — ок; `my-super-skill` — нет.
2. **Description** — начинается с глагола и говорит *когда применять*, а не
   что скил делает в теории. Описывает суть механики (так, чтобы из описания
   харнесс мог понять триггер).
3. **`when:` — конкретный.** Х HemisphereTrigger-ситуация, не абстрактная
   категория. `«баг ревьюет первый взгляд / intermittent flake / регрессия»`
   лучше, чем `«отладка»`. Это строчка, по которой харнесс решит активацию.
4. **Скил самодостаточен.** Агент должен выполнить его, прочитав только
   SKILL.md (плюс profile.json/spec/CONTEXT.md, на которые можно ссылаться).
5. **Правила — обязательные требования**, не пожелания. Если правило можно
   нарушить без последствий — оно не правило, убери.
6. **Механика, не вещание.** Конкретные таблицы, чек-листы, форматы вывода,
   anti-паттерны, escalation-триггеры. Не «будь внимателен» — а «default to
   flagging; Block если нет regression-теста на новое поведение».
7. **Источники — укажи** (номинально в комментариях или в «Что дальше»),
   откуда механика (mattpocock / emilkowalski / auto-improve / …), но не
   копируй предметку — адаптируй.

## Результат

- `skills/library/<name>/SKILL.md` (или `skills/<name>/` для ядра) создан.
- Frontmatter: name + description + when.
- Разделы: Когда применять, Правила, Цикл, Результат (минимум).
- Новое имя добавлено в таблицу библиотеки AGENTS.md и README/README.ru
  (это делает `stitch`/main после `skill-add` — не обязательно в момент
  создания, но валидатор expects его).
- Запусти `scripts/validate.sh` — должен быть зелёным.

## Что дальше

- Если проект часто нуждается в этом скиле — `stitch` его активирует в
  `.agent-forge/skills.json`.
- Если скил оказался избыточен — удали + обнови таблицы.
