# spec — спецификация из разговора

Профиль зафиксирован. Теперь сверни разговор и понимание кодовой базы в
**построимую спецификацию**. Это синтез, **не интервью** — не задавай новых
вопросов, используй то, что уже есть в `profile.json`, `CONTEXT.md` и
разговоре. Если чего-то не хватает — вернись к `grilling`, не додумывай.

## Когда применять

- После `grilling` (или `wayfinder`, когда карта прояснилась — `spec`
  «сворачивает» карту связанных решений в построимый план).
- Перед `to-tickets`/`implement`.

## Правила

1. **Синтез, не интервью.** Никаких новых вопросов пользователю. Неизвестное —
   в `grilling` или пометь как `openRisk`/`wayfinder`.
2. **Use ubiquitous language.** Термины из `CONTEXT.md` — в spec-текст и
   user stories дословно. Никаких технических синонимов.
3. **Out-of-scope — отдельно, жёстко.** Всё из `profile.outOfScope` переносится
   в `## Out of Scope`. В implementation decisions не попадает никогда.
4. **No file paths / code snippets** в spec (кроме состояния/схемы, полученной
   из prototype — то кодирует решение точнее прозы; trim до decision-rich).
   Пути быстро устареют.
5. **Seams** — согласуй с пользователем. Минимум seams, приоритет existing.
   Идеальное число = 1, на самом высоком уровне.
6. Spec публикуется в issue-tracker проекта (из `profile.stack.tracker`) с
   меткой «ready»: на github — issue, на local — `.scratch/<feature>/spec.md`.

## Шаблон spec

```
## Problem Statement
<проблема с точки зрения пользователя>

## Solution
<решение с точки зрения пользователя>

## User Stories
Длинный нумерованный список. Каждая: «Как <actor>, я хочу <feature>,
чтобы <benefit>». Покрыть все аспекты — экстенсивно.

## Implementation Decisions
- модули (построить/изменить)
- интерфейсы этих модулей
- технические уточнения
- архитектурные решения (→ ADR для hard-to-reverse)
- изменения схемы
- контракты API
Без путей к файлам. Состояние/схема из prototype — инлайн с пометкой источника.

## Testing Decisions
- что хороший тест (поведение через public, не internal)
- какие модули тестируются
- prior art (похожие тесты в кодовой базе)

## Out of Scope
<из profile.outOfScope — дословно>

## Further Notes
<остальное>
```

## Результат / критерий готовности

- `spec` опубликован в issue-tracker (или `.scratch/<feature>/spec.md`).
- Метка «ready» на нём.
- Каждый пункт `profile.outOfScope` отражён в `## Out of Scope`.
- Seams согласованы с пользователем.
- Дальше: `wayfinder` если нужна карта, `to-tickets` если это
  multi-session build, `implement` если влезает в одну сессию.
