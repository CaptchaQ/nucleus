# review — code-review двух осей

Сам ревьюишь свой код — слеп. Ревью **двумя свежими субагентами** по двум
осям ломает слепоту: один смотрит на совпадение со стилем/паттернами проекта,
второй — на совпадение с spec/user-stories. Каждый читает дифф свежим
глазом, без стерилизации контекста. Сводка по двум осям — тебе, и вердикт.

## Когда применять

- После `implement`до коммита фичи.
- Закрываешь branch/PR против fixed point (review сам по себе).
- НЕ ревьюий сразу после написания в том же окне — свежий взгляд обязателен.

## Правила

1. **Две оси, два субагента.** Standards и Spec — отдельные проходы,
   параллельно. Не совмещай в одном: у каждой оси свои критерии.
2. **Default to flagging, одобрение заработано.** Review настроен флагать по
   умолчанию — Block/Approve по критериям, не «кажется ок».
3. **Обязательный формат вывода.** Review выдаёт **таблицу**:

   ```
   | Before | After | Why |
   |--------|-------|-----|
   | <что было / где> | <что нужно> | <почему это баг-риск / какой критерий нарушен> |
   ```

   Списком ЗАПРЕЩЕНО — таблица держит дисциплину: каждое замечание = локус +
   правка + основание. Plus **вердикт**: `Block` (есть Block-замечания) или
   `Approve` (только nitpick или ничего).
4. **Escalation-триггеры** — чёрный список, который сразу флагит Block (примеры
   для цели проекта допиши из `profile.qualityGuardrails`): нет теста на новое
   поведение, мутация public-контракта без ADR, утечка internal в public,
   tautological-тест, implementation-coupled тест, отсутствие out-of-scope
   проверки, изобретённое значение (duration/spacing/easing не из catalog).
5. **Reviewer не пишет код за implementer.** Reviewer предлагает правку в
   After, но не применяет — implementer правит, reviewer не подменяет.
6. **Одно замечание — одна идея.** Не слепи compound (как в grilling).

## Механика

### Standards-ось (стиль/паттерны)

Субагент проверяет:
- соответствие стилю проекта (linter, naming, паттерны из существующего кода);
- deep-module-форма (поведение за маленьким интерфейсом, не плоский модуль);
- seams — не появилось ли тестов против internal (должны быть на public);
- дубль-код / 外文名ные функции / leak абстракции;
- не появилось ли `transition:all`-подобных рефлексов (по `profile.qualityGuardrails`).

### Spec-ось (контракт/user-stories)

Субагент проверяет против spec/user-stories:
- каждая user-story покрывается диффом (поведение через public, не internal);
- out-of-scope не просочился в код;
- testing decisions из spec соблюдены (seams согласованы, prior art reused);
- breaking-change контракта помечен ADR;
- термины — ubiquitous language из `CONTEXT.md`, не технические синонимы.

### Сводка

Собери два отчёта в единый вердикт:
- `Block` — есть хоть один Block-замечание от любой оси → implementer чинит,
  потом **новый** review (fresh окно, не тот же).
- `Approve` — только nitpick или чисто → коммит/merge.
- Если обе оси чисты — короткое подтверждение, «Approve: 0 Block,
  нитпиков N».

## Цикл

1. Подготовь дифф (branch vs base). Убедись, что spec/user-stories/spec
   доступен субагентам (профиль + spec + CONTEXT.md).
2. Запусти **параллельно**: субагент-Standards, субагент-Spec. Каждому дай
   дифф, профиль/spec/, `CONTEXT.md`, контракт роли, обязательный формат
   (таблица + вердикт) и escalation-триггеры.
3. Собери отчёты → единая таблица Before/After/Why по двум осям + вердикт.
4. Если `Block` → список правок implementer, новый проход review. Если
   `Approve` → коммит и переход к следующему тикету/spec.

## Результат / критерий готовности

- Два отчёта (Standards + Spec) в таблице Before/After/Why.
- Единый вердикт Block/Approve на экране.
- Block-замечания превращены в правки implementer,Approve-проход повторён
  свежими субагентами.
- При Approve — commit. post-mortem Block-замечаний в
  `.agent-forge/improvements.md` (если паттерн повторяется — кандидат на
  новый скил или escalation-триггер в `profile.qualityGuardrails`).
