# domain — доменная модель (CONTEXT.md + ADR)

Actively build & sharpen the project's domain model. Это **активная**
дисциплина — challenge terms, invent edge-case scenarios, write glossary и
decisions в момент кристаллизации. (Просто *прочитать* `CONTEXT.md` ради
лексики — это однострочный habit любого скила, не domain-скил. Этот скил —
когда ты **меняешь** модель, не просто потребляешь.)

## Когда применять

- В `grilling` когда появился термин / решение кристаллизуется.
- Нужно зафиксировать hard-to-reverse архитектурное решение.
- Термин в разговоре конфликтует с существующим `CONTEXT.md`.
- Другой скил поддерживает домен-модель (ему нужен single source of truth).

## File structure

Один контекст (default):

```
/
├── CONTEXT.md         ← глоссарий: определения терминов
└── docs/
    └── adr/
        ├── 0001-event-sourced-orders.md
        └── 0002-postgres-for-write-model.md
```

Если контекстов несколько — `CONTEXT-MAP.md` у корня указывает где каждый
живёт (на поддомены).

Создавай файлы лениво: нет `CONTEXT.md` — создай при первом термине. Нет
`docs/adr/` — создай при первом ADR.

## Правила

### Challenge против глоссария

Когда человек использует термин, конфликтующий с `CONTEXT.md` — подними
сразу: «Твой глоссарий определяет 'cancellation' как X, но ты, кажется,
имеешь в виду Y — что правильно?»

### Zаточи fuzzy language

Человек использует vagе/перегруженный термин — предложи precise canonical
term: «Ты говоришь 'account' — ты имеешь в виду Customer или User? Это
разные вещи». Один canonical term на концепцию.

### Обсуждай конкретные сценарии

Когда обсуждаются отношения домена — stress-test их сценариями. Изобретай
edge-case сценарии, которые форсят человека быть точным по границам концептов.

### Cross-reference с кодом

Человек говорит «как что-то работает» — проверь, согласен ли код. Найдя
противоречие, подними: «Твой код отменяет целые Orders, но ты сказал что
partial cancellation возможен — что правильно?»

### Update CONTEXT.md inline

Когда термин resolved — обнови `CONTEXT.md` **тут же**, не батчируй. Формат:

```markdown
# <Проект>

## Language

**<Термин>**:
<каноническое определение, без деталей реализации; одна концепция на термин>.
_Avoid_: <альтернативы которые больше не используются и почему>

## Relationships

- <A> содержит много <B>
- <B> несёт один <роль>

## Flagged ambiguities

- <недоразумение между двумя терминами> — resolved: <как>
```

`CONTEXT.md` **вне** деталей реализации. Это глоссарий, не spec/scratchpad.

### ADR sparingly

Предложи ADR только когда выполнены **все три**:

1. **Hard to reverse** — стоимость передумать meaningful.
2. **Surprising without context** — будущий читатель спросит «почему так?».
3. **Result of a real trade-off** — были альтернативы, выбрали одну по
   конкретным причинам.

Если хоть одно отсутствует — пропусти ADR. Формат:

```markdown
# ADR-NNNN — <title>

## Status
Accepted (YYYY-MM-DD)

## Context
<ситуация, forces, альтернативы>

## Decision
<что решили и почему; что не решили>

## Consequences
<последствия: появилось, исчезло, риски>
```

## Результат / критерий готовности

- `CONTEXT.md` существует, содержит каждый resolved термин с определением
  (no implementation details).
- `docs/adr/NNNN-slug.md` для каждого hard-to-reverse решения.
- Другие скилы (`grilling`/`spec`/`review`/`wayfinder`) могут тянуть из
  `CONTEXT.md` ubiquitous language дословно.
- Конфликт термин/код — в поднятом замечании (не молча).

## Чего избегать

- `CONTEXT.md` как spec — нет, это глоссарий.
- ADR на каждое решение — нет, только hard-to-reverse + surprising + real
  trade-off.
- Батчить обновления глоссария — пиши в момент.
