# orchestrate — оркестр субагентов

Когда задача покрывает несколько слоёв (фронт + бэк + тесты + доки) или
слишком велика для одного прохода — распредели её по **ролям** и
**параллельным субагентам** с чёткими границами и обязательным форматом
вывода. Так работа идёт на автомате, а ты собираешь артефакты, а не пишешь всё
сам в одном окне.

## Когда применять

- Этап плна требует нескольких видов работы одновременно.
- Один проход «написать всё сразу» даст необозримый дифф и загрязнённый контекст.
- Нужен свежий взгляд (review) — его нельзя совместить с написанием.

## Роли

| Роль | Владеет | Не делает |
|------|---------|-----------|
| **planner** | декомпозицией, порядком, критериями готовности | не пишет код |
| **researcher** | поиском фактов (API, версии, best practices) | не проектирует |
| **implementer** | кодом под контракт (профиль+план+spec) | не меняет контракт |
| **reviewer** | свежим взглядом: баги, пропуски, качество | не пишет код за implementer |
| **tester** | запуском, сценариями, ошибками | не «докидывает фичи» |
| **designer** | UX/UI-решениями (если домен это допускает) | не трогает бизнес-логику |
| **docs** | README, CONTEXT, комментарии интерфейсов | не рефакторит код |

## Механики

1. **Контракт — профиль + spec + plan.** Все роли работают по одним
   `profile.json` / `CONTEXT.md` / `pln.md` / spec. Роль не меняет контракт —
   только предлагает, решение за человеком.
2. **Порядок жёсткий:** planner → (researcher) → implementer → reviewer →
   tester → (docs). Не перескакивай: reviewer не начинается, пока implementer
   не закончил.
3. **Одна роль — один проход.** Не совмещай implementer и reviewer в одном
   окне — свежий взгляд требует смены контекста.
4. **Результат роли — артефакт**, а не «поговорили»: код, заметка, список
   багов, отчёт. Артефакты — в `.agent-forge/` или в коде проекта.
5. **Параллельные субагенты для независимой работы.** Когда задачи не
   зависят друг от друга — запускай их параллельно как субагентов. Примеры:
   - **review двумя осями**: один субагент-Standards (соответствие стилю/патернам),
     второй-Spec (соответствие spec/user-stories). Без стерилизации контекста —
     каждый читает свежий diff. Сводка по двум осям — тебе.
   - **аudit-then-plan**: capable-модель делает реконaise → рекурсивно
     спавнит параллельных субагентов по категориям (perf / a11y / security /
     consistency) → каждый пишет находки в свой точечный отчёт → ты net/
     prioritize (high-leverage сначала) → пишешь **self-contained планы**
     для исполнения (в т.ч. дешёвой моделью): каждый план = inline-clamped
     значения, пути, куски кода в начале, `NNN-slug.md`, `plans/README.md` с
     порядком исполнения.
6. **Self-contained план = артефакт оркестра.** План должен быть исполним
   свежим агентом без твоего контекста: все нужные значения inline, точные
   пути, ожидаемый результат, критерий готовности. Не «посмотри в spec» —
   дай всё на месте (по Emmil: cut to extract, inline-clamped).

## Режимы

### Под рукой (один харнесс, есть субагенты)

- Каждой роли — отдельный субагент или свежее окно.
- Перед ролью дай: профиль, spec, текущее состояние репо, **контракт роли**
  (что владеет, чего не делает), обязательный формат вывода.
- После каждой роли — сверка с планом: этап движется к цели?

### Без субагентов (последовательно)

- Роли идут последовательно в одном окне, но с явными phase-boundary
  (continue / clear / compact — см. ниже). Не совмещай.
- Свежий взгляд для review: `/clear` или compact передて.

## Phase boundaries (между ролями)

На границе фазы — выбери один (по приоритету):

- **Continue** — остаться. Стоит первым проверить и отвергнуть.
- **Subagent** — тесно зачищённый task в своё окно, отчёт обратно.
- **`/compact`** — сжать контекст и продолжить (default на дне дерева).
- **`/clear`** — пустое окно, когда здесь ничего не нужно дальше.
- **Handoff** — portable markdown в другое окно/харнесс/коллегу.

## Что НЕ делать

- Не запускать reviewer и implementer в одном окне — ломает свежий взгляд.
- Не плодить роли ради.process — маленькая задача (одна сессия) идёт через
  `implement` напрямую, без оркестра.
- Не терять артефакты ролей — каждый отчёт должен где-то лежать (код,
  `.agent-forge/`, issue-tracker).
- Не поручать субагенту менять shared-контракт — он работает по нему, не
  правит.

## Результат / критерий готовности

- Этап выполнен: каждый артефакт роли на месте (код / отчёт ревью / план).
- Ревью двух осей (Standards+Spec) дало единый вердикт, замечания либо
  починены implementer, либо приняли как риски в spec.
- Self-contained планы (если были) исполнены (возможно дешёвой моделью) без
  необходимости твоего контекста — это и есть «работа на автомате».
- Дальше — следующий этап плна или handoff на человека (если дошли до края
  карты wayfinder).
